# Procedure

Budget: **8 tool calls**. Spend them as: 1 collection, 1 skill loading, 1 verification, 2–4 fixes, 0 spare. Never read a file the diff already showed.

## 1. Collect (one bash call)

Run from the repository root. If the workspace holds several independent repos, loop over each one that has a `.git`.

```bash
git status --porcelain=v1 -uall
git diff HEAD --stat
git diff HEAD -- . ':(exclude)*lock*' ':(exclude)dist' ':(exclude)build' ':(exclude)*.min.*' | head -700
for f in $(git ls-files --others --exclude-standard | grep -E '\.(ts|tsx|js|jsx|py|go|rs|java|cs|rb|php|sql|json|md)$'); do
  echo "----- $f"; cat -n "$f" | head -120
done
```

Generated files never enter the review: lockfiles, build output, route trees, API clients generated by codegen, migration snapshots. Detect them by header comments (`generated`, `do not edit`) and by the project's codegen config. Judge translation JSON by the diff, never by opening the whole file.

If the diff was truncated by `head`, say so only when a relevant file was cut.

## 2. Pick the side and load the skills (one call)

Decide from the changed paths which side(s) changed (backend, frontend, both) and which skills apply. See [skill-routing.md](skill-routing.md).

Locate the installed skills with one command, in this order: `.claude/skills`, `.agents/skills` in the project, then in the user's home. Skill folders may be nested inside a section folder (`backend/`, `frontend/`, `workflow/`).

For each matched skill, read **only** its `SKILL.md`. Its core rules are the checklist for those files. Open a `references/` file only when a finding depends on a detail in it. If no skills are installed, review with the common checklist alone and say so in the report.

The project's own fixed rules (`AGENTS.md`, `CLAUDE.md`, lint config, architecture tests) take precedence when they conflict with a skill.

## 3. Verify (one call, greps grouped)

Every finding needs evidence. Join all greps into a single bash call.

```bash
echo "== usage of X =="; grep -rn "ExportName\|path/to/file" src | grep -v "the-file-itself"
echo "== duplicate of Y =="; grep -rn "characteristic-snippet" src
```

No evidence means do not report it, or mark it **suspect** and say what is missing.

Common false positives: route files registered by a file-based router, framework modules registered by convention, decorators-based wiring and barrel `index.ts` re-exports have no explicit importer and are not dead code.

## 4. Analyze

Apply, in this order:

1. The core rules of each matched skill, against the files that skill covers.
2. The [common checklist](common-checklist.md): dead code, duplication, flawed logic.

Severity:

- 🔴 **BLOCKS**: real bug, runtime break, fixed rule violated, exposed secret, missing tenant or permission guard.
- 🟡 **ADJUST**: pattern violated, duplication, dead code or file.
- 🔵 **OPINION**: optional improvement.

Violations of a rule that a skill marks as fixed, "no exception" or "always" are 🔴 and are never downgraded.

## 5. Fix what is mechanical

Fix on your own, following the project's architecture, when the fix is **obvious and closed in scope**:

- move a file to the correct level and update every import that pointed to it;
- rename a file or export to the convention;
- extract a visible string literal to the correct translation file;
- remove an unused import, variable, prop, export or translation key;
- replace a hardcoded value with a constant or key that already exists;
- expand a spread that crosses a persistence or external boundary into explicit fields, only when the source fields are visible in the file;
- extract a helper declared inside a component to its proper file.

**Do not fix, only report:**

- anything that needs a product, API or architecture decision;
- deduplication that changes a public signature or touches 3+ files beyond the move;
- rewrites of logic whose intent is unclear;
- anything marked as suspect.

After a fix, check that no import still points to the old path (grep inside the verification call). Never run lint, build or tsc to validate: it is not allowed.

## 6. Output

Only what changes the reader's action. No "out of scope" section, no list of what was not run, no narration of calls used, no confirmation of what was fine.

```
## <repo or area>

### Fixed
path/file.tsx:42 — <what was wrong> → <what was done>.

### Pending
path/other.tsx:8 — 🔴 BLOCKS: <defect>. <fix>. Not fixed: <reason>.
path/more.ts:15 — 🟡 ADJUST: <defect>. <fix>. Not fixed: <reason>.

**Verdict:** <ready to commit | N blockers pending>
```

If a relevant file (auth, payments, database writes) was cut by the diff limit and you could not read the rest within budget, it goes in as pending: `path/file.ts — 🟡 NOT REVIEWED: file cut by the diff limit, re-read before approving.`

Include 🔵 only for a specific, useful finding. No praise, no summary of what the diff does, no "overall it looks good". Nothing outside the diff unless the diff broke it.
