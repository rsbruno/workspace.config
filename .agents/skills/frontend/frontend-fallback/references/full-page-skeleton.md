# Full-page fallback: dedicated fallback shells and generic primitives

When building a full-page fallback (one that covers header + filter + content at once, whether via a route `pendingComponent` or `if (isPending) return <PageFallback />` in the component), never instantiate live business components. Use dedicated structural fallback siblings (`PageRootFallback`, `PageHeaderRootFallback`, `TableFallbackRoot`) and generic field primitives (`TextFieldFallback`, `ComboboxFallback`, `BadgeFallback`, `ButtonFallback`, or the local equivalents). These components are inert, have no business side effects and preserve the loaded screen's geometry.

The only thing that can be mirrored from the real screen is the **purely structural shell**. Anything that carries text, value, dynamic icon, or state is represented by a dedicated fallback primitive, never by the live field, badge, button, input, avatar or formatted-value component.

**If the codebase already has an established pattern of reusing real components with a `loading` prop in a full-page fallback, do not repeat it.** Extract or use a dedicated fallback sibling instead. The project convention that matters is the local fallback primitive and shell family, not a live component's loading mode.

> **Failure to avoid:** an edit-form fallback built by instantiating the real components of each form section, all receiving a `loading` prop via Context. Most fields (via a generic primitive) and some sections became skeletons correctly, but a side panel's `Typography` and `Button` never received `loading` and showed real text over an otherwise gray form. There is no type or lint error for this, only a visual bug. Rewriting the fallback as pure `Skeleton`, with no dependency on every real component forwarding `loading`, makes this class of hole impossible by construction. Lesson: a `loading` prop cascading through real components is an implicit, fragile contract; a full-page fallback built from pure skeletons has no exception for any project convention.
