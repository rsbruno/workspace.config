# Extrapolating screen bounds with fade-out ("translucent" effect)

When the design calls for a full-page skeleton to intentionally extrapolate beyond the card/page bounds (downward and/or sideways) and fade out instead of ending in a hard edge, this becomes a reusable shell component in the design system — never an ad-hoc `<div className="...">` copy-pasted into every fallback file. Real project example: `PageFallbackOverflow` at `src/components/ui/fallbacks/page-fallback-overflow.tsx` — applies negative margin (extrapolates), a height ceiling (`max-h-[calc(100vh-Xrem)]`) with `overflow-hidden`, and a translucent mask via `mask-image`/`style.maskImage` (bottom-to-top gradient: opaque at the bottom, transparent at the top) — combinable with a second mask (`maskComposite: "intersect"`) that fades the side edges when content has real horizontal overflow. Every page fallback that needs this effect wraps `PageRoot` with this component instead of hand-rewriting the mask/margins. If the project doesn't have a component like this yet and the design asks for the effect, create an analogous one (any name, same idea: reusable overflow+mask shell) instead of inlining it per fallback.

# Reusable mirror components for real pieces repeated across screens

When a real visual piece (not a generic design-system primitive, but a composition — e.g. `Person` = avatar + name + subtitle) repeats across multiple screens/table columns, create a sibling `*Fallback` component in the same reusable-fallbacks directory of the design system (e.g. `src/components/ui/fallbacks/`), with **the same prop signature** as the real component (including props that would be required in the real one, made optional in the fallback since the value is never used) — but the body is 100% `Skeleton`/primitives with `loading`, never reading the received values. This keeps Rule 2 (a real piece never accepts its own `loading` prop) while still giving a one-line component to import into any table/list fallback that uses that piece, instead of recopying the skeleton structure every time. Real example: `PersonFallback` next to `Person` (`src/components/table/person/`), reproducing avatar + two text lines with the same relative sizes, exported from the same barrel (`ui/fallbacks/index.ts`) as `PageFallbackOverflow`.

# Even pure shell/layout components get their own `*Fallback` sibling — no `loading` prop, ever, on any real component

Superseded decision, keep for history: this doc used to allow a `loading` prop on purely structural shell components (header, border, container) that only swap a CSS class with no data. **That exception is retired.** Reason: the goal of a fallback is zero ongoing maintenance — a `loading` prop on a real component is one more thing every future consumer must remember to pass, and it silently rots the moment one screen forgets it (exactly the failure class Rule 1 exists to prevent, content or not). So the rule is now uniform, no carve-outs by content vs. shell:

**Every real component that has more than one trivial rendering — content or pure layout shell alike — gets a sibling `*Fallback` component, colocated in the same folder, exported from the same barrel.** The real component never receives `loading`/`isLoading` as a prop, full stop. The only pieces allowed to keep a native `loading` prop are the generic, leaf-level design-system primitives with no children composition of their own (`Skeleton`, `Typography`, `Button`, `Avatar`, `FieldContainer`, and equivalents) — these are the atoms every `*Fallback` sibling is built out of, not something to add a fallback wrapper around.

Examples of shells, all following the same shape (`fallback.tsx` next to the real file, same folder, re-exported from that folder's `index.ts`):

- `PageHeaderFallback` — `src/components/ui/page/header/page-header-fallback.tsx`, mirrors `PageHeaderRoot` + `PageHeaderContent` (title + subtitle lines), optional `back` prop mirrors `PageHeaderBack`. Gray top border instead of primary.
- `SearchbarField`'s loading shape belongs to the listing fallback toolbar; do not invent a `PageSearchRoot`/`PageSearchFallback` family when the project uses `SearchbarField`.
- `PageRootFallback` — `src/components/ui/page/root/page-root-fallback.tsx`, sibling of `PageRoot`, adds the translucent overflow/mask shell (see the "Extrapolating screen bounds" pattern above) with zero props required.
- `TabsListFallback` — `src/components/ui/tabs/fallback.tsx`, sibling of `TabsList`/`TabsTrigger`. Takes one prop, `widths: string[]` (one Tailwind width class per tab) — unavoidable, since the real tab count/label length is exactly the one thing that varies per screen and can't be inferred generically. Renders one `TypographyFallback` per width, same `border-b`/`gap`/`px` chrome as the real `TabsList`.
- `TableFallbackRoot` / `TableFallbackRow` — `src/components/ui/table/fallback.tsx`, siblings of `TableRoot`/table row chrome. Zero props beyond `children`/`className` — the row's cell skeletons (which vary per column, per entity) are passed as children by the screen's own fallback, but the repeated card/padding/border wrapper never gets rewritten by hand again.

**Minimizing manual props is the actual goal, not a nice-to-have.** Before shipping a new `*Fallback` sibling, check whether it can hit zero required props (pure structural chrome — `PageRootFallback`, `TableFallbackRoot`) before reaching for one unavoidable prop (`widths` on `TabsListFallback`, because content-derived count truly can't be known generically) — and never reintroduce a `loading` boolean as a shortcut instead of building the sibling component. A fallback file that needs no manual sizing/count props per usage is the one that won't need touching again when the real screen changes.
