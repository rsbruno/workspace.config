# Rule 1 — Loading is ALWAYS a dedicated fallback component, never a `loading` prop cascading through real components

Every loading state (whole route, section, card, side panel, whatever) is solved by building its own `*Fallback`/`*Skeleton` component and doing an early-return/`pendingComponent` to it — never by reusing the screen's real components with a `loading`/`isLoading` prop passed directly or through Context to "turn off" their content. That cascade is always an implicit, fragile contract: it only takes ONE real component along the way forgetting to forward the prop (a `Typography`, a `Button`, a side panel) to leak real content over the skeleton, with no type or lint error flagging it. A dedicated fallback eliminates this whole bug class by construction — always the first thing to check/decide before touching any loading code.

# Rule 2 — Strip any scattered skeleton logic out of the real code

Whoever draws the loading state is the fallback component, full stop — no real business component of the screen (form section, card, list item, panel) should have its own `loading`/`isLoading` prop, an internal `if (loading) return <Skeleton/>` conditional, or a Context carrying that state into the real component tree. When fixing a skeleton, always sweep the screen's real components (form/section root, context, every subcomponent) for these leftovers — an accepted-and-propagated `loading` prop, a `useXContext` exposing `loading`, a conditional like `<Then><Skeleton/></Then><Else>{children}</Else>` outside the generic design system — and remove all of it: prop signature, Context field, JSX propagation, now-unused imports. **Only exception**: generic, leaf-level design-system primitives (the local equivalent of `Skeleton`, `Typography`, `FieldContainer`, `Avatar`, `Button`) that already expose `loading` as part of their contract for any screen in the system to use — those aren't "scattered logic", they're the infrastructure piece every dedicated fallback (Rule 1) is built out of. What's forbidden is any *composite* component having its own notion of "I'm loading" — and that's not limited to business/content pieces: a purely structural shell (a header root, a tabs list, a page root, a table row wrapper) is just as forbidden from taking `loading` as a form section or a list item. See `reusable-shells.md` — even pure-layout shells get their own `*Fallback` sibling now, no exception by "it's just a CSS class swap." That responsibility is 100% the fallback file's, for every composite component without exception.

> **Failure that motivates these two rules:** an edit screen had a correct skeleton-only `pendingComponent` at the route level, but its component also mounted the real form tree with `loading={isPending}` cascading through Context for the client-side load. Fields looked right (via a generic primitive), but the side panel never forwarded `loading` to its inner `Typography`/`Button`, so on reload the panel showed a real avatar, name and button while the rest of the screen was skeletonized. The root cause was not a wrong fallback but the cascading `loading` prop itself: any forgotten component is a silent bug. Fix by removing `loading` from every real component and relying only on the dedicated fallback.
