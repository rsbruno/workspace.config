# One fallback per content shape — never a generic one for divergent shapes

When a screen has multiple visual content shapes (day/week/month of a calendar, tabs with different layouts, list vs kanban), **each shape gets its own fallback file**, named mirroring the real view's file/component. Never reuse a shared generic fallback across views with divergent visual structures (hour columns vs. calendar grid vs. list) — a "few gray bars" fallback serving day, week, and month views alike (three completely different layouts) is exactly the bug class this skill exists to prevent.

**A boolean prop toggling a shape inside one fallback component is the same bug, just disguised.** `<EntityFormFallback tabs />` vs `<EntityFormFallback />` conditionally rendering `<TabsListFallback />` inside is one file quietly serving two divergent shapes — same violation as the calendar example above, just with an `if` instead of a second file. When a form fallback needs to exist both with and without a tab strip (a create route with no tabs, an edit route with tabs), split it into two components: `EntityFormFallback` (no tabs) and `EntityFormWithTabsFallback` (with tabs) — never `EntityFormFallback({ tabs }: { tabs?: boolean })`. Same rule for any other shape-toggling boolean on a fallback (`compact`, `withSidebar`, `withFilters`, etc.) — each combination that's actually used by a route gets its own named component, not a flag threaded through one.

Each view-specific fallback replicates that view's real structure (same number of columns/rows, same auxiliary column like hour/category, same proportions), with some blocks filled in (not uniformly empty) to look like real content about to appear — vary the position/size of fake "item" blocks instead of a robotic uniform pattern, but deterministically (fixed indices), never randomly (the skeleton must not change shape on every render).

# Real overflow must still exist — only the scrolling itself gets disabled

When real content in a list/grid/carousel/board naturally overflows its container (more columns/items than fit in the visible width/height, with scroll — horizontal or vertical) — **the skeleton reproduces that overflow too, never shrinking/resizing items to fit everything without spillover.** Showing just a cut-off "sliver" of the next item/column at the edge is the visual cue telling the user "this scrolls, there's more" — and that "large content" feeling needs to already be present during loading, or the layout jumps (from "fits everything" to the real, scrollable version) the moment data arrives.

So: **keep the same fixed width/height as each real item** (don't switch to `flex-1`/flexible sizing just to "fit nicely") — that's what makes the overflow happen the same way as the real thing. What changes is only the ability to scroll: during loading, scrolling is **disabled** (the container clips the excess, no scrollbar, can't drag/scroll) — because there's no point letting the user scroll to see more empty placeholders while there's no data yet. In practice: switch the container's overflow property from "scrollable" (`overflow-x-auto`/`overflow-y-auto`/`overflow-auto`, or the project's equivalent) to "clipped, no scroll" (`overflow-hidden`/`overflow-x-hidden`/`overflow-y-hidden`) only in the fallback — keeping each item's fixed dimensions intact, so the clip happens at the same place/proportion it would with real data.

One-line summary: **the skeleton should look large and full, with a sliver of item cut off at the edge signaling "there's more" — it just shouldn't let the user actually scroll there while there's no data yet.**

# Table/list fallback

Replicates the real row's columns exactly: same avatar/icon when present, same order, same relative column width, same cell type (text, badge, action button). Repeats the row a plausible number of times (whatever pattern the project already uses for this, typically 5-8). Never fewer columns or less information than the real row — if the real row has avatar + name + subtitle + phone + status + action, the skeleton has exactly those 6 positions.
